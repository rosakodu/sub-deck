# Руководство по сборке, выпуску релизов и стабильности сетевого стека (sub-deck)

Данный документ описывает правила архитектуры, системные требования SteamOS и регламент подготовки релизов для плагина **sub-deck**. Соблюдение этих правил гарантирует стабильную работу у конечных пользователей без сбоев сети, зависаний и проблем «холодного старта».

---

## 1. Архитектурные требования к автономности (Offline-First)

### Проблема «холодного старта»
Большинство пользователей устанавливают VPN на Steam Deck именно в условиях, когда доступ к зарубежным ресурсам (включая `github.com` и `objects.githubusercontent.com`) заблокирован или сильно замедлен.
Если релизный архив не содержит скомпилированных бинарников и гео-баз, плагин пытается загрузить их на лету через `urllib.request`. В результате первый запуск туннеля завершается ошибкой по тайм-ауту.

### Обязательные требования к дистрибутиву:
1. **Каталог `defaults/bin/` обязан содержать бинарники под архитектуру `linux/amd64`:**
   * `sing-box` (поддержка Hysteria 2, TUIC v5, Cloudflare WARP WireGuard)
   * `tun2socks` (создание L3 виртуального TUN-интерфейса `tun0`)
   * `xray` (поддержка VLESS Reality, VMess, Trojan, Shadowsocks)
2. **Каталог `defaults/` обязан содержать предзагруженные гео-базы:**
   * `geosite.dat` и `geoip.dat` (для маршрутизации Xray-core)
   * `geosite.db` и `geoip.db` (для маршрутизации sing-box / RoscomVPN)
3. **Логика восстановления в коде (`core/binaries.py`):**
   * Функции `ensure_xray_and_tun()`, `ensure_singbox()` и `update_geofiles()` обязаны **всегда в первую очередь** проверять локальный каталог `defaults/` и распаковывать файлы оттуда, обращаясь к GitHub только в качестве крайнего запасного варианта.

## 2. Специфика SteamOS: Спящий режим (Sleep/Resume) и сетевой стек

### Механика спящего режима в Steam Deck
Пользователи часто блокируют/усыпляют консоль кнопкой питания прямо во время игры или загрузки.
При засыпании сетевой адаптер Wi-Fi обесточивается, сокеты ядра рвутся. При пробуждении:
1. Wi-Fi переподключается заново; шлюз (`gw_ip`) и локальный IP-адрес могут измениться.
2. Если в системе останется старый интерфейс `tun0` с наивысшим приоритетом (`default dev tun0 metric 1`), трафик пойдет в «мертвый» туннель, и пользователь останется без интернета.

### Реализованная защита:
1. **Фоновый монитор сна (`main.py:_sleep_monitor_loop`):**
   * Отслеживает дельту времени через `time.monotonic()`. Если интервал проверки (3 сек) превысил 8 секунд — зафиксировано пробуждение консоли.
   * Если до сна VPN был включен, монитор ожидает до 10 секунд появления шлюза Wi-Fi (`get_default_gateway()`).
   * При появлении шлюза вызывается автоматический перезапуск туннеля на новом интерфейсе (`self.vpn.start(node)`).
   * Если сеть недоступна (например, консоль включили в самолете или офлайн), плагин вызывает `self.vpn.stop()` и снимает маршрут `tun0`, предотвращая сетевой лок.
2. **Очистка «хвостов» при старте (`vpn_manager.py:cleanup_stale`):**
   * При каждом запуске или перезапуске плагина вызывается принудительная очистка:
     * `resolvectl revert tun0` (сброс системного DNS)
     * `ip route del default dev tun0 metric 1`
     * `ip link delete tun0`
     * Завершение зависших процессов `xray`, `tun2socks`, `sing-box`.

## 3. Маршрутизация и совместимость с другим софтом

### Конфликты с Zapret / GoodbyeDPI
* На Steam Deck в РФ у многих пользователей установлен плагин `zapret-deck`, использующий NFQUEUE/divert через `iptables`/`nftables`.
* Одновременная работа полного туннеля (`tun0`) и `zapret` может приводить к дублированию модификации пакетов и сбоям TLS.
* Рекомендуется отключать `zapret` при использовании полного туннеля (`default`). В режимах «Обход РФ» (`bypass_ru`) и «RoscomVPN» (`roscomvpn`) трафик к российским ресурсам идет напрямую.

### Изоляция DNS
* Маршрутизация DNS настраивается исключительно через `systemd-resolved` командами:
  ```bash
  resolvectl dns tun0 <DNS_SERVERS>
  resolvectl domain tun0 ~.
  resolvectl default-route tun0 yes
  ```
* Запрещается напрямую перезаписывать файл `/etc/resolv.conf`, так как в SteamOS это приведет к поломке штатного резолвера NetworkManager.

## 5. Автоматизированная сборка релиза

Для подготовки релиза используется скрипт:
```bash
./build_release.sh
```

### Что выполняет скрипт:
1. **Тестирование:** запускает полный набор unit-тестов (`python3 -m unittest discover tests`).
2. **Сборка React UI:** собирает фронтенд через Rollup (`pnpm run build`), генерируя актуальный `dist/index.js`.
3. **Верификация офлайн-компонентов:** проверяет наличие бинарников `xray`, `tun2socks`, `sing-box` и гео-баз в каталоге `defaults/`.
4. **Фильтрация:** исключает исходники, кэши (`__pycache__`, `.pyc`), тесты и `node_modules`.
5. **Нормализация прав:** выставляет `chmod 755` на каталоги и бинарники, `644` на файлы.
6. **Упаковка:** формирует zip-архив с единым корневым каталогом `sub-deck/`, готовым для Decky Loader:
   * `out/sub-deck-v<ВЕРСИЯ>.zip`
   * `out/sub-deck.zip` (символический alias)
7. **Хеширование:** вычисляет и выводит SHA256 контрольную сумму.

- [ ] Запущен `./build_release.sh` без предупреждений и ошибок.
- [ ] Проверен деплой на тестовый Steam Deck:
  ```bash
  ./deploy.sh <IP_STEAM_DECK>
  ```
- [ ] Проверен статус через сокет:
  ```bash
  ssh deck@<IP_STEAM_DECK> "curl -s --unix-socket /tmp/sub-deck.sock http://localhost/api/status"
  ```
  Версия должна совпадать с номером релиза, `"running": false`.
- [ ] Проверено подключение к серверу (например, WARP или VLESS Reality) и отключение.
- [ ] Проверено переключение всех 4 пресетов маршрутизации:
  * `default` (По умолчанию / Весь трафик)
  * `bypass_ru` (Обход РФ и LAN)
  * `gaming` (Игровой)
  * `roscomvpn` (RoscomVPN / Антизапрет)
- [ ] Проверен спящий режим: консоль усыплена на 15 секунд при включенном VPN, после пробуждения сеть восстанавливается автоматически.

